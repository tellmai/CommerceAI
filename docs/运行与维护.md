# 运行与维护

## 数据目录和身份

`.env` 保存生成的数据库和工作台访问口令；`.local/admin-password` 便于本机用户查看访问口令，权限600，不提交Git。浏览器会话12小时，退出后失效。默认仅监听本机，远程部署需要另行配置HTTPS、访问范围和账号设计。

原生数据库位于 `.local/pgdata`，只在 `.local/pgsocket` 私有目录提供Unix socket。API和worker各单进程；前端为编译后静态文件，由API提供。Docker模式使用独立数据库及证据卷，由Nginx提供静态文件，数据库不映射主机端口。

平台连接默认关闭。若自行启用，密钥位于存储目录的 `private/market-connection.json`，文件权限为 600，数据库及普通备份不含该文件。迁移或恢复后可通过 **找货与比价 → 平台连接** 重新填写。人工报价与分析报告随数据库备份。

当前原生连接可设置为：

```bash
export DATABASE_URL="postgresql+psycopg://commerceai@/commerceai?host=$PWD/.local/pgsocket&port=55432"
```

数据库程序由 PyPI `pgserver==0.1.4` 的隔离二进制提供，当前实测 PostgreSQL 16.2。Compose 使用官方 PostgreSQL 16 镜像。系统 Docker 在本次环境中需要管理员密码，本机尚未安装；容器构建与恢复已在 GitHub CI 验证，本机资源以原生测量为准。

## 启停

Docker 首次由管理员执行 `sudo bash scripts/install-docker.sh`，正常用户执行 `python3 scripts/setup.py` 和 `bash scripts/start.sh`。启动脚本在需要时通过sudo调用Docker，停止使用 `bash scripts/stop.sh`。普通停止不会删除卷；不要为停机使用删除卷的命令。

原生环境首次 `bash scripts/bootstrap-native.sh`，以后 `.venv/bin/python scripts/native.py start` 和 `stop`。启动时执行迁移和幂等演示初始化；真实经营和公开历史不会被演示初始化覆盖。

所有模拟记录需要重新生成时，先停止API和worker、启动独立数据库，再显式执行 `scripts/reset_demo.py --confirm-demo-only`。该操作只重置demo；不会删除public/live，但会清除模拟空间中的手工演练记录。

## 备份与恢复验证

先暂停写入与后台任务，备份应同时包含数据库和证据文件。数据库备份排除会话数据，恢复后重新登录。

原生模式：

```bash
.venv/bin/python scripts/native.py stop
.venv/bin/python scripts/devdb.py
export DATABASE_URL="postgresql+psycopg://commerceai@/commerceai?host=$PWD/.local/pgsocket&port=55432"
.venv/bin/python scripts/backup.py
.venv/bin/python scripts/restore_check.py .local/backups/实际备份文件.tar.gz
.venv/bin/python scripts/native.py start
```

恢复验证只允许创建全新的 `_restorecheck` 数据库，已有数据库拒绝覆盖；校验数据库摘要、证据文件和会话为空，并重定位导入文件路径。不会替换正在使用的数据库。需要真正恢复工作台时，先保留原数据，再按恢复结果切换连接和存储目录，验证后重启。

Docker模式：`bash scripts/backup-compose.sh` 会暂停API/worker，导出数据库和证据，再恢复服务。`bash scripts/restore-compose.sh 备份目录` 使用独立 `commerceai-restorecheck` 项目及8081端口，不使用原项目卷。当前电脑尚未执行容器恢复；GitHub CI 已完成四容器构建、启动和独立恢复验证，原生恢复及远程记录见验收报告。

## 资源配置

Compose内存上限：数据库768MiB、API512MiB、worker768MiB、前端128MiB。数据库使用128MB共享缓冲、4MB工作内存、最多20个连接；API小连接池，任务并发1。原生模式采用同样数据库和进程配置，但不受容器内存硬限制。

空闲及导入实测见 `benchmark.json`，常规浏览器操作实测见 `normal-memory.json`；可在操作期间执行 `.venv/bin/python scripts/measure_resources.py --seconds 30` 复测。PSS按共享内存比例计算，覆盖API、worker和整个PostgreSQL实例；不包含浏览器、构建和操作系统文件缓存。测量不是对所有数据规模的保证。需要降低后台占用时停止工作台，数据保留。

## 故障排查

- 登录提示未配置：运行初始化脚本，重启服务，使环境变量加载。不要将真实口令写入README或截图。
- 来源/证据失效：核对启用状态、授权范围、有效期和证据版本，补充新审核；不要修改历史评分掩盖问题。
- 导入失败：查看任务错误码和错误行。超过10万行先拆分；超过20MB不增加默认内存处理，先准备小批文件。
- 前端暂时读不到后端：检查原生 `.local/api.log`、`.local/worker.log`、`.local/postgres.log` 或 Compose 日志和健康状态。
- 本机启动已有PID记录：先确认实际进程，再执行停止脚本，不直接删除数据库目录。
- 原生端口8000占用：检查是否已有工作台；不要结束与本项目无关的进程。
- 平台接口拒绝请求：核对所选平台权限、配额、淘宝路由和 Token。无可用账号时可在真实经营空间人工登记报价。

浏览器回归运行独立测试服务，默认使用 8010 端口。先构建前端，再指定以 `_test` 结尾的 PostgreSQL 数据库和独立 `DATA_DIR`，执行 `npm --prefix frontend run test:e2e`。可用 `E2E_CHROMIUM` 指向本机 Chromium 可执行文件。

日志只记录必要请求/任务标识和错误类型；不记录口令、Cookie、完整导入行或客户联系方式。原始文件包含业务信息时应按本机数据同等保护。
