# 设计决策

## ADR 001 模块化单体与低资源运行

采用单API、单worker、PostgreSQL队列和静态前端。首版没有Redis、消息队列、向量库或本地大模型，降低常驻占用。Docker为可复现部署路径；本机缺少管理员密码时提供同一业务代码的原生PostgreSQL备用路径，不引入SQLite替代生产数据库验证。

## ADR 002 类型合同和统一修订存储

业务资源采用独立Pydantic模型及OpenAPI合同，持久化采用带类型的JSONB实体、关系表和追加式修订。业务规则集中在应用服务，复合关系外键确保空间一致。统一存储让样品、报价、风险、订单和评分共享版本/审计语义，替代V1.0的逐表草案。代价是部分业务字段约束由合同和服务校验；禁止绕过API直接写业务JSON。

## ADR 003 三种数据空间

将模拟、公开历史与真实经营隔离到所有业务记录及关系；单用户可切换三个空间。这是来源隔离，不是SaaS租户设计。公开历史不进入真实经营指标，也不填充不存在的成本。

## ADR 004 阶段条件与评分独立

研究、买样、样品通过、测款准备逐阶段审核，解决先有样品才能评分、先有完整评分才能买样的前置条件循环。硬风险、费用和履约审核优先于评分，正式操作检查当前证据，不依赖过去评分。

## ADR 005 合同由代码导出

OpenAPI从FastAPI定义生成，前端类型从OpenAPI生成，SQL从Alembic导出，字段字典从Pydantic合同生成。运行参数主文件在config目录，docs保存同步副本，减少独立手工版本发生漂移。
